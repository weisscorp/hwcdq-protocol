# Live BLE evidence: 2026-08-25

This record preserves the staged real-device evidence obtained with the
packaged macOS client. The first process reached advertisement, connection, and
GATT discovery. A corrected monitoring-only process later subscribed,
authenticated, and repeatedly read configuration and telemetry. Neither of
those two historical runs sent voltage/current/Start/Stop or an unknown opcode.
A later desktop build did accidentally send output-control value zero while
still in monitoring mode; that separately preserved incident corrects the
command polarity below.

### Public sanitization

The public evidence intentionally withholds the sampled charger's serial
number, advertised name, MAC/CoreBluetooth identifier, and raw configuration
identity field. Live telemetry frames that contain no identity-bearing bytes
remain documented as live captures. This preserves the protocol conclusion
without publishing a device fingerprint.

### HW178P identity and control-range provenance

The live 103-byte configuration payload provides two upper-limit fields whose
offsets were independently recovered from the APK parser:

| Payload offset | Raw bytes | Decoded value | Evidence status |
| ---: | --- | ---: | --- |
| `33` | `00 00 32 43` | `178.0 V` maximum voltage | confirmed static parser plus live packet |
| `37` | `00 00 60 41` | `14.0 A` maximum single-module current | confirmed static parser plus live packet |

On 2026-08-25 the owner identified this charger/product as **Pidzoom Portable
charger HW178P** and supplied its `50…178 V` operating-voltage range and `14 A`
current maximum. The protocol packet itself does not contain the model identity
or a minimum-voltage field. Consequently, `50 V` is retained as owner-supplied
model evidence rather than a decoded protocol fact. The desktop client's
`0.01 A` lower bound is a conservative positive application floor and is not
claimed as a hardware-proven minimum.

The trace contains 129 opcode-`0x06` request starts, 123 matched responses, and
127 checksum-valid telemetry frames. Five requests reached the then-configured
three-second response deadline, and the final request hit the native write
deadline. The surplus valid frames are important: without a sequence field, a
late response cannot be distinguished from a response to the next same-opcode
request.

## Output-state polarity correction

The historic desktop decoder interpreted the captured state byte `1` as
`output_enabled:true`. That derived JSON field is demonstrably wrong:

- `VALUES.fromByteBloc` places payload byte `+36` in object field `+0x4f`;
- the AOT Open/Close row at `0x486a20` loads that field at `0x486ad4` and maps
  raw `1` to Close/off and raw `0` to Open/on;
- the physical charger display showed 4.076 V, 0.000 A, and an inactive output
  indicator during this telemetry; the owner explicitly confirmed that output
  was OFF;
- the separately recovered output callback loads the current state at
  `0x487490`, maps raw `1` to argument `0` and raw `0` to argument `1`, loads
  opcode `0x0C` at `0x487500`, and calls the generic int32 setter at `0x487504`.

The corrected protocol rule is strict: telemetry raw `0` = ON/Open, raw `1` =
OFF/Close, every other byte = unknown. Two owner-supplied device photographs
and the desktop screenshot were not copied into the repository, but are
identified for evidence continuity:

## Output-control incident and command-polarity correction

The ignored local diagnostic
`logs/charger-live-20260825-wnr-final.jsonl` was inspected at exactly 363,345
bytes, SHA-256
`53c30f5a909ce10a0cc0a6483ee676cb9fc0bd6759acd0201c97b0b502087c7a`,
PID `7487`. The full JSONL is not copied into the repository because it contains
local identifiers. No credential bytes are reproduced here.

This event chain is decisive:

| Sequence | Evidence |
| ---: | --- |
| `1` | `application_started` recorded `output_controls_enabled:false`; this was monitoring mode. |
| `331` | checksum-valid `0x06` telemetry: raw state `1` = OFF, output `4.084536552429199 V`, `0 A`. |
| `349` | client transmitted exact frame `06 0C 00 00 00 00 0C`. |
| `359` | charger returned `03 0C 01 0D`; payload `01` acknowledges acceptance only. |
| `378` | next checksum-valid telemetry reported raw state `0` = ON; output voltage had not yet risen from `4.084536552429199 V`. |
| `432` | raw state remained `0`; output voltage rose to `17.819053649902344 V`. |
| `462` | raw state remained `0`; output voltage reached `134.1124725341797 V`. |

Only the fields needed for this inference are reproduced. The pre-command and
first post-command frames were:

```text
seq 331, telemetry OFF
30 06 00 78 64 43 00 00 00 00 00 85 48 42 00 06 08 42
00 00 1C 42 86 B4 82 40 00 00 00 00 00 00 00 00 00 00
00 00 01 00 00 00 00 00 00 00 00 01 E0

seq 349, output-control request
06 0C 00 00 00 00 0C

seq 359, acceptance ACK
03 0C 01 0D

seq 378, telemetry ON
30 06 00 F0 63 43 00 00 00 00 00 7A 48 42 00 06 08 42
00 00 1C 42 86 B4 82 40 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 01 4B
```

The voltage ramp independently rules out a presentation-only state change.
Therefore opcode `0x0C` int32le `0` = energize/Start/ON is **confirmed**. The
AOT callback's complementary mapping gives int32le `1` =
de-energize/Stop/OFF with **high confidence**, but frame
`06 0C 01 00 00 00 0D` has not yet been transmitted to this charger and is not
labelled live-confirmed. The `01` ACK payload cannot be interpreted as returned
state; only subsequent `0x06` telemetry establishes state.

The command was transmitted despite monitoring mode. This is evidence of a
desktop-client authorization bug, not permission for monitoring clients to
mutate hardware. The corrected product rule is that authentication and read
requests are the only monitoring writes; `0x07`, `0x08`, and `0x0C` all require
explicit output-controls mode. Stop additionally requires fresh telemetry
explicitly reporting ON, though it does not depend on V/I/setpoint readiness.

## Acknowledged-write failure and WNR boundary

The PID 67357 build used `write_with_response:true`. Transaction `tx-000133`
started its single `02 06 06` FFE3 write, but CoreBluetooth never delivered
the corresponding write-completion callback before the three-second native
deadline (sequence `3261`). The client marked the native handle poisoned at
sequence `3265` and completed best-effort teardown with
`transport_connected:false` at sequence `3276`. Valid FFE2 application
responses had often arrived before earlier acknowledged-write completions, so
the transport callback was not a reliable proxy for application progress.

Because live FFE3 advertises WNR with maximum 253 and all normal requests fit
inside it, the rebuilt independent client now prefers WNR and retains
acknowledged write only when WNR is absent. This policy was implemented after
the captured run. **Real-device WNR long-run durability is not yet verified**;
it awaits the bounded, read-only soak in `../docs/live-testing.md`. A passive
Android HCI capture is still required to establish the original application's
effective ATT write type.

## Conclusions and limits

- Live-confirmed: FFE1 parent; FFE2 RX notification; FFE3 TX; authentication
  acceptance; firmware/serial/config/telemetry framing and checksums; decoded
  `0x05` maxima `178 V`/`14 A`; exact telemetry state polarity on the sampled
  OFF device.
- Live-confirmed output-control value: opcode `0x0C` int32le zero energizes/starts
  output. Voltage/current setters remain static-only; int32le-one Stop is high
  confidence from AOT and not yet live-transmitted.
- Implemented client policy, awaiting hardware soak: WNR preference, five-second
  telemetry maintenance, 60-second configuration refresh, eight-second
  response deadline, and 1/2/5-second read-only reconnect.
- A response timeout must invalidate the link. Same-opcode retry on the same
  sequence-less stream can consume a late prior response and is unsafe.
- Unknown, calibration, password-change, factory, and firmware-update commands
  remain unavailable and were not transmitted.
